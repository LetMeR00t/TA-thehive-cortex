# Release Notes - v5.1.0

## Summary

Live inputs stop losing time. Until now each run asked TheHive for exactly the
last interval and kept no state: a run that failed, hung, was skipped or asked a
little too early lost its window for good. From this release every pull remembers
where it stopped, and the next run continues from there.

This release also repairs four bugs found running 5.0.0 against TheHive 5.6.7
behind a proxy. All of it was contributed by **Matt C**
([@mjc420](https://github.com/mjc420), pull requests #138 and #139); the commits
keep their authorship.

## Fixes

* **A collected object without `_createdAt` or `_updatedAt` no longer drops the
  run.** TheHive leaves a date out when it has no value. All five collectors
  (alerts, cases, observables, audit, tasks) now stamp `_time` from the requested
  date, else `_createdAt`, else `_updatedAt`, else the collection time, and log
  WARNING `TH127` with the missing date and the *names* of the fields present.
  A `date_field` of a tasks input is accepted with or without its leading `_`.
* **One TTP per technique.** Splunk ES findings that annotate several techniques
  produced a single procedure (`T1110, T1078`) that TheHive rejected
  (`TTPS_FAILED`), so the alert was created with none. A multivalue `ttp` field
  now gives one TTP per value too.
* **TheHive unreachable fails fast.** Connecting has its own 10 s timeout, and a
  request that timed out while reading is no longer sent again (a POST could be
  created twice). Connection errors and 500/502/503/504 answers are still retried.

## New: watermark per input pull

* Each pull keeps the end of the last window it collected completely, in the KV
  store collection `thehive_cortex_checkpoints`. A run collects
  `[watermark, now - lag)`; the watermark moves only after every event was written,
  so a failed run is caught up by the next one.
* **Search head cluster:** only the captain collects (INFO `SKIP` elsewhere); the
  KV store replicates the watermarks, so a new captain carries on.
* **KV store disabled** (some heavy forwarders): watermarks go to the input's
  checkpoint directory, on that instance only (WARNING `KV`). **KV store not ready:**
  the run does not collect (WARNING `KVWAIT`) and the next one catches up.
* Two optional settings on alerts & cases, audit, observables, tasks and timeline
  inputs: `lag_seconds` (default 60) and `max_catchup_seconds` (default 21600).
* New log identifiers: `WIN`, `DONE`, `SKIP`, `KV`, `KVWAIT`, `KVOPEN`, `CKPT`,
  `TH127` (see `docs/log_ids.md`).

## Upgrading

* No input needs a change. Without a watermark, the first run collects one interval
  ending `lag` seconds ago, which is what 5.0.0 collected, a minute later: no gap
  and no flood.
* The first run after the upgrade creates the KV collection; the add-on's role
  needs write access to it (`admin`, `sc_admin`, as in `default.meta`).
* Events collected up to the upgrade are not collected again.

## Known issues

* AppInspect (precert) flags `check_for_custom_mako_templates`: a `future_failure`
  in 4.3.0, a `warning` in 4.3.1 (zero failure and zero error in both). It points at
  `appserver/templates/base.html`, deprecated in
  Splunk 10.4. The file is generated by `ucc-gen`, not by this repository, and UCC
  6.6.0 (the version that builds this release) still emits it even though the message
  advises 6.3.0 or later. Nothing fails today; the fix depends on a future UCC release.
