# Release Notes - v5.0.0

> ⚠️ **Not tagged yet.** This file is written as the work lands, not at tagging
> time: an upgrade instruction remembered at tagging time is an upgrade
> instruction lost.

## Summary

A major, and the number is deliberate. Nothing in the add-on's shape changes —
same commands, same alert actions, same parameters — but several things it
**did** were wrong, and correcting them changes what you will see.

Three of them are worth knowing before you upgrade:

* **Objects are no longer created CRITICAL and TLP:WHITE by default.** The
  dropdowns had no default value, so Splunk selected the first choice.
* **Fifteen log identifiers changed**, each of them one that designated two
  different events at once. A correspondence table is below.
* **The command logs get their sourcetype back** — and that one needs a manual
  step on your side, or the fix will look inert.

Everything else is repair: two dashboards that could not display anything since
v4.0.0, three panels querying a sourcetype this add-on never produced, an alert
action framework that reported success as failure, and a debug line that wrote
part of an API key into the logs.

## ⚠️ Manual step required after upgrading — sourcetypes of the add-on logs

### What was broken

Since **v4.0.0**, the search commands write their log as
`TA-thehive-cortex_<command>.log`, but `props.conf` still enumerated the
**v3.x** file names. The result: **23 of the add-on's 27 log files carried no
sourcetype at all**, and Splunk auto-learned one from the file name instead —
which is where `..-2`, `..-3` and `..-too_small` sourcetypes come from.

The symptom was misleading, and that is why it survived three minor versions:
the four `*_modalert` stanzas kept matching, so `props.conf` still looked
alive. Only the search commands were affected — plus, unnoticed until now, the
`thehive_create_a_new_alert` and `thehive_run_function` alert actions, which
never had a stanza of their own.

`props.conf` now matches the **shape** of the name rather than a list of
today's commands, so a command added tomorrow is covered on the day it ships.
The sourcetype `tathehivecortex:log` is also **defined** at last: until now it
was assigned everywhere and described nowhere, so line breaking and
timestamping fell back to Splunk's defaults on a format that begins with a
plain ISO date.

### 🖐️ What you must do — otherwise the fix will look like it did nothing

Once Splunk has **learned** a sourcetype it persists it into
`$SPLUNK_HOME/etc/apps/learned/local/props.conf`, as an **exact**
`[source::<full path>]` stanza. An exact-path stanza is *more specific* than
the wildcard stanza this add-on ships, so **it keeps winning** after the
upgrade.

1. Open `$SPLUNK_HOME/etc/apps/learned/local/props.conf`.
2. Remove every stanza whose source path points at a
   `TA-thehive-cortex_*.log` or a `*_modalert.log` file.
3. Restart Splunk.

Events indexed **before** the upgrade keep the sourcetype they were indexed
with — a sourcetype is decided at index time and is not rewritten
retroactively. To search across both, use the source rather than the
sourcetype:

```
index=_internal source=*TA-thehive-cortex_*.log
```

### Migration instructions of v4.0.0 are readable again

`release_notes/v4.0.0.md` disappeared in **v4.2.0**, while v4.2.0, v4.2.1 and
v4.2.2 all linked to it with a **relative** link — which resolves inside the
current tag, where the file no longer existed. Those instructions are labelled
*mandatory*, so the file is restored rather than the link rewritten: a relative
link to an absent file would break again at the next tag.


## 🔧 The Job SID guard on the Cases and Alerts views actually guards

The **Job SID** field of the *create* panels was gated by a check that only
tested for an empty string. Three ways around it, all closed now:

* **A single space** set the token and unlocked the action, dropping
  `| loadjob` into the very error the guard exists to avoid. The test is on
  blanks now, not on `""`.
* **A value carried in by the URL or a drilldown** never passed through the
  change handler at all, because a handler does not fire for a value an input
  already holds. An `<init>` block now clears the token at load.
* **An expired SID** was well formed and therefore accepted — search jobs
  expire, and the failure surfaced deep inside the alert action. The view now
  checks that the job still exists on this search head and says so, in place,
  keeping the action locked meanwhile.

⚠️ **Small compatibility note:** if you had a bookmark or a drilldown
pre-filling `create_sid_set` to skip the field, it no longer works. That is
precisely the hole being closed.


## 🔧 A refused TTP no longer fails an alert that was created

If the account this add-on uses lacks the **`manageProcedure`** permission,
TheHive refuses the MITRE TTPs — and the exception used to escape the alert
action. The result: the alert **was created**, the action exited with code 5,
`splunkd.log` reddened on every single run, and nothing in that output said
that only the TTPs were missing.

Now the failure is caught where it happens and named:

```
[THCA-133] TTPS_REFUSED - object ~1234 was created, but its TTPs were REFUSED:
the account is missing the `manageProcedure` permission on this organisation.
```

The action reports the creation it actually performed. ⚠️ **This is a TheHive
profile setting** — grant `manageProcedure` to that account's profile on that
organisation; there is nothing to change in the add-on. Any other failure of
the same call is reported as `134`, with the server's raw error.


## ⚠️ Shape change: collected alerts now carry their TTPs

The **TheHive: Alerts & Cases** input (and its backfill) offers **TTPs** under
"Additional information" for alerts and cases alike. For alerts, the choice was
saved and then **dropped at every run**: only cases ever came back with their
procedures, and nothing said why.

If an input has **TTPs** ticked, each collected **alert** event now gains a
`ttps` field (the alert's procedures, as for cases). Nothing disappears, but a
search that counts or lists an alert event's keys will see one more. Inputs
without **TTPs** ticked are unchanged.


## ⚠️ Breaking (and a repair): `cortexjobs` stops confusing "running" with "empty"

### What was wrong

The command asked Cortex for a job's report **without looking at the job's
status**. A job still being analysed answers with an empty report, and that
empty report was written out exactly like an analyzer that had found nothing.
Two different facts, one identical line — and no way to tell them apart from
the search results.

Two calls the vendored library has always offered were never made:

* `job/{id}/waitreport?atMost=` — Cortex holds the answer server-side until the
  job finishes or the delay expires. One call, instead of a polling loop.
* `job/{id}/artifacts` — the observables the analyzer **extracted**. This is the
  enrichment Cortex produces, and it never came back to Splunk.

### What changes in your results

| New field | Meaning |
| :--- | :--- |
| `cortex_job_finished` | `1` for `Success` / `Failure` / `Deleted`, `0` while running |
| `cortex_job_artifacts` | the extracted observables, as `dataType::value` |
| `cortex_job_artifacts_count` | how many |

⚠️ **A row with `cortex_job_finished = 0` no longer carries a
`cortex_job_report` field at all** — an absent field cannot be mistaken for an
empty answer, an empty list can. **A saved search that counts rows will see its
count change**; filter on `cortex_job_finished = 1` if you meant finished jobs.

A finished job with no report at all (`Deleted`) used to raise a `KeyError` and
lose the whole search. So did a job whose `createdAt` or `updatedAt` was
missing. Both now produce a row.

### New setting: **Cortex Job Max Wait (seconds)**

Default `0` — answer immediately, the behaviour of every previous version. Set
it, or pass a `wait` field to `cortexjobs`, to let Cortex hold the answer.
⚠️ Keep it below the **HTTP Timeout**, which bounds each single call.


## ⚠️ Breaking: the datatypes lookup moves to the KV store

### What changes for your searches

| What you write | After the upgrade |
| :--- | :--- |
| `\| inputlookup thehive_datatypes` | ✅ unchanged |
| `\| inputlookup thehive_datatypes.csv` | ❌ **drop the `.csv`** |

The lookup definition keeps its name — `[thehive_datatypes]` never carried the
extension — so only searches spelling out the file name are affected. The
dashboard panel shipped with the add-on has been corrected.

### Why it had to move

The add-on wrote its datatypes into
`$SPLUNK_HOME/etc/apps/TA-thehive-cortex/lookups/thehive_datatypes.csv`, which
has three consequences, all real:

* that directory is **replaced on every upgrade of the add-on** — so the care
  the code takes to preserve the rows you customised was undone by the next
  upgrade;
* writing there is **refused by Splunk Cloud vetting**;
* it is **not replicated across a search head cluster**, so what an alert
  action learned on one member was invisible to the others.

The KV store has none of the three, and this add-on already used it for
`cortex_analyzers` — the mechanism is not new here, only newly applied.

### What you have to do: nothing

On the first alert action after the upgrade, if the collection is empty and the
old CSV is still on disk, **its rows are migrated as they are** — including the
custom-field mappings you added by hand. The migration happens once; afterwards
the CSV is ignored and kept only as the seed of a fresh installation.

⚠️ If that first run reports `THC-9` or `THC-17`, the migration did **not**
happen: your customised rows are still in the CSV alone. Fix what the message
names, empty the collection, and let the next run seed it again.

### And a refresh no longer waits a day

The old code refreshed the file when it was more than 24 hours old. A KV store
document has no modification time, so the refresh now happens **once per search
execution** instead — the same cost as the custom field definitions read beside
it, and a datatype added in TheHive shows up on your next search rather than
the next day.


## ⚠️ Breaking: some log identifiers changed

Fifteen identifiers designated **two call sites at once**, which makes them
useless for the one thing they exist for: tracing an incident back to a line.
`135` labelled a TTPs success *and* an observable failure in the same file;
`140` a TTPs failure *and* the start of attachment processing.

Only the **second** occurrence of each was renumbered, so a search built on the
first still matches. Scope was kept minimal on purpose: gaps in the numbering
are left alone -- a gap bothers nobody, a collision does.

If you have saved searches or alerts keyed on one of these, update them:

| module | was | now | that site is |
| :--- | :--- | :--- | :--- |
| `backfill_alerts_cases.py` | `MI-ERR` | `MI-ERR-DATES` | the date range could not be parsed |
| `backfill_alerts_cases.py` | `MI-ERR` | `MI-ERR-COLLECT` | the collection itself failed |
| `backfill_audit.py` | `MI-ERR` | `MI-ERR-DATES` | the date range could not be parsed |
| `backfill_audit.py` | `MI-ERR` | `MI-ERR-COLLECT` | the collection itself failed |
| `common.py` | `S30` | `S32` | the resolved instance is returned |
| `common.py` | `S45` | `S46` | reading `thehive_max_cases` |
| `common.py` | `S54` | `S58` | reading `thehive_creation_max_retry` |
| `thehive.py` | `TH1` | `TH2` | the detected TheHive version |
| `thehive.py` | `TH30` | `TH31` | password AND API key are both empty |
| `thehive.py` | `TH40` | `TH41` | the connection test request |
| `thehive.py` | `TH50` | `TH51` | the connection succeeded |
| `thehive.py` | `TH115` | `TH118` | a case number could not be resolved |
| `thehive.py` | `TH139` | `TH141` | tasks recovered, with their filters |

`docs/log_ids.md` lists every identifier the add-on can emit. It is generated

## 🔒 A secret fragment no longer reaches the logs

`thehive.py` logged `Secret length: N, ends with: XXXX` at debug level -- the
last four characters of the API key, into a file Splunk indexes and anyone with
access to the index can read. It now logs the length alone, which is what
distinguishes "empty" from "truncated" from "looks right".

If you have run this add-on at debug level, those lines are in your index. They
expire with your retention; purging them earlier is a local decision.


## 🖥️ Three dashboards now do what they always claimed

### `TheHive: Statistics` displayed nothing at all

Two panels carried `depends="$always_hidden$"`, a token nothing ever set. A
hidden panel does not run its search — and those two searches were the only
producers of the tokens the main chart consumed. The chart waited for input
forever: no error, no "no results", just a pie that never filled. This has been
the case since **v4.0.0**, when the other two views were migrated and this one
was overlooked.

⚠️ A side effect worth knowing: the old date handling compared against the
literal `1970-01-01T01:00:00.000+01:00`. That sentinel only matched on a server
in UTC+1 outside summer time, so the "all time" branch was unreachable
elsewhere. The view now derives its range from the time picker directly, like
the Cases and Alerts views.

### `TheHive: Alerts` opened empty

The results panel was gated on a token that only the Action input's *change*
handler produces — and a change handler does not fire for the value an input
already carries at load. The Action selector said "LIST" while no list existed:
you had to pick another mode and come back. Its twin, the Cases view, has no
such gate, which is how two nearly identical views ended up behaving in
opposite ways.

### `Cortex: Analyzers` — REFRESH now refreshes

The only panel that runs `cortexrefreshanalyzers` and rewrites the analyzer
lookup was gated on **Debug = Yes**. Choosing Action = REFRESH turned the status
banner red on "Waiting for input" and did nothing else — the refresh ran only
for someone who also switched Debug on, with no indication anywhere that the two
were linked.

The panel is now gated on the action that asks for it. ⚠️ **The Debug control is
removed**: with the gate corrected it drove nothing at all, and a switch a user
can flip with no visible effect is worse than no switch. The panel's sub-title
also claimed the search "is used to add a new instance", which it never did.


## 🖥️ `Audit Logs` — three panels out of five showed nothing

They searched `sourcetype="modular_alerts:thehive_*"`, a sourcetype **this
add-on has never produced**. `props.conf` assigns `tathehivecortex:log` to those
very files, and has since v4.0.0. The panels returned "No results found" on
every installation, and the action filter above them was permanently empty.

⚠️ Two smaller faults went with it. The base read
`(index=_* OR index=cim_*) sourcetype="A" OR sourcetype="B"` — where the
implicit AND binds tighter than the OR, so the second branch carried **no index
constraint at all** and scanned the user's default indexes. And the success
series had no colour, because the palette mapped a label the search never
produced.

The "commands versus modular inputs" split was also wrong: it guessed from the
file name, testing for `search`, `get` or `run`. `cortex_refresh_analyzers`
contains none of them and was filed under modular inputs, where the label table
did not know it and showed a raw file name. The split now keys on the `MI-`
prefix the code itself writes into every modular input's log line.

Finally, the event-code chart only extracted codes starting with `CAA-`, which
covers the alert-action framework and nothing else — every code from the add-on
proper (`THCA`, `THAO`, `THSC`, `MI-THAC`, `CRA`…) was invisible, while the
sub-title promised "the complete list of event codes".

## 🔧 Every dashboard search now goes through a macro

The five existing macros never named an index, deliberately: which index holds
TheHive data differs from one deployment to the next. That convention now covers
the add-on's own logs too, through a sixth macro, `thehive_cortex_logs`, and
every panel of the Audit view uses it.

**What this means for you.** If a log panel comes back empty while the files
exist on disk, add your index to the macro once:

```
[thehive_cortex_logs]
definition = index=_internal sourcetype="tathehivecortex:log"
```

⚠️ The add-on's logs land in `_internal`, which is not among the default search
indexes of every role. Naming the index in nine separate panels — as the view
did before — means re-editing the view at every upgrade, which is how local
changes get lost.

## 🔧 `thehive_tasks` was missing the tasks collected per case

The macro covered `thehive:tasks:*` but not `thehive:cases:tasks:*`, which
`props.conf` defines and the modular input writes. A search built on it returned
results — just not all of them, which is the kind of gap nobody notices.


## ⚠️ Breaking (and a good thing): Severity, TLP and PAP now default sensibly

The Severity, TLP and PAP dropdowns of the create-a-case and create-an-alert
forms carried **no `<default>`**. Splunk then selects the first `<choice>` —
which was `CRITICAL (!!) - 4` for severity and `WHITE - 0` for TLP and PAP.

Every case and every alert created without touching those three fields was
therefore **critical, and marked shareable with anyone**. The asterisk in the
labels ("Severity*") suggested the field mattered but forced no conscious
choice.

The defaults are now MEDIUM, AMBER and AMBER — TheHive's own.

🖥️ **If you rely on the old behaviour**, set the values explicitly in your
saved searches: an alert action that never named `param.severity` will now
create MEDIUM cases where it used to create CRITICAL ones.


## ✅ The MITRE catalogue setting finally does something

`thehive_ttp_catalog_name` was exposed on the Settings page, read by the code,
handed over — and consumed by nobody. Changing it did nothing at all.

Meanwhile a TTP's `patternId` was validated by checking it starts with `T`,
which accepts `T`, `TOTO` and `T99999` alike. A wrong id was accepted by the
add-on and rejected by TheHive afterwards, in a message naming neither the row
nor the field it came from.

The setting that was doing nothing existed precisely for the check that was
missing. A `patternId` absent from the configured catalogue is now dropped with
a message naming **which id** (`THC-122`), instead of being sent for TheHive to
refuse.

⚠️ **An unreachable catalogue does not block anything.** If it cannot be read,
the ids are forwarded unchecked and a warning says so (`THC-120`). Refusing
would mean an outage on our side silently dropping legitimate TTPs — punishing
you for our own failure. The catalogue is read **once per execution**, not once
per row.

🖥️ If you use TTPs and have never set a catalogue name, nothing changes: with no
catalogue configured there is nothing to check against.


## ⚡ Two invariants read once per execution instead of once per row

`parse_events` re-read the custom field definitions (an HTTP round-trip to
TheHive) and the datatypes lookup (a full CSV re-read) on **every call**.

Harmless for the creation actions, which call it once. Not harmless for
**"Add observables"**, which calls it once per result row: for a search
returning 1 000 rows, that is ~1 000 identical HTTP calls and ~1 000 CSV
re-reads — and, when the datatypes file is more than 24 hours old, ~1 000
attempts to rewrite it under `$SPLUNK_HOME/etc/apps` from an alert action
worker.

Both are now memoised per execution, keyed on the instance URL: a search
addressing two TheHive instances still reads each one's catalogue.

⚠️ Nothing changes in what the actions produce. A test counts the calls, since
this cost is invisible both in a reading and in a unit test that runs one row.


## 🔧 Alert action parameters: the declaration now matches the code

`globalConfig.json` has no `alerts` section — the six forms are hand-written
HTML — so the `.conf` declaration, the form and the code were three independent
statements about the same parameter. Four had drifted:

* **`cortex_instance_id` and `analyzers`** were read by the Cortex action and
  declared nowhere. Splunk does not pass an undeclared parameter, so the code
  received `None`. ⚠️ For `analyzers`, marked *required* in the form, that meant
  `.replace()` on `None` — an `AttributeError` instead of a message naming the
  missing field.
* **`thehive_run_function` declared `param.title`**, while the form posts `name`
  and the code reads `name`. The declared parameter did not exist; the one that
  exists was not declared.
* **`param.sighted_field = 0`** — this holds a *field name*, and `"0"` is truthy.
  It forced `sighted = False` on **every observable**, silently inverting the
  documented default of `sighted = True`. 🖥️ If you never touched that field,
  observables will now be created as *sighted*, which is what the documentation
  always said.
* The Cortex action was the only one whose `param._cam` omitted
  `supports_adhoc`, so it did not appear where the other five did.


## ✨ The Audit view refreshes itself

Its five panels now refresh every 60 seconds. It reads the Splunk index, so a
cycle costs the TheHive server nothing.

⚠️ **Deliberately nowhere else.** The Cases and Alerts views call the TheHive
API on every render: a 60-second refresh there would mean one HTTP round-trip
per minute *per open tab*, and on their "run the action" panels it would create
an object every cycle. Those keep an explicit refresh, done by you.
