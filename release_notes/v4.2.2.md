# Release Notes - v4.2.2: "The Pollen Sieve" 🌼

## Summary
Version 4.2.2 is a **bug-fix release** about things that used to fall through
without a sound. A custom field of type `url` was dropped from every alert and
case with no error at all; an empty "Job SID" let the create action fail deep
inside the add-on instead of stopping at the form. Both are fixed, and the
add-on now **says something** when it drops a custom field instead of staying
silent. Splunk Cloud administrators (`sc_admin`) also regain write access to
the views and navigation.

No new feature is introduced and no configuration change is required — this is
a safe, drop-in update from v4.2.1.

## Improvements & Bug Fixes

### 🧩 Alert Actions: `url` custom fields are no longer dropped ([#133](https://github.com/LetMeR00t/TA-thehive-cortex/issues/133))
- **Root cause**: custom field values are only forwarded when their type is
  recognised by a chain handling `string`, `boolean`, `integer`, `float` and
  `date`. The `url` type, available since TheHive 5.1, was missing from that
  chain, so the field was skipped. The alert or case was still created, minus
  the field, and **nothing was logged** — the value simply never arrived.
- **Fix**: `url` carries a plain string value and is now handled exactly like
  `string`. Both "Create a new alert" and "Create a new case" are affected, as
  they share the same parsing routine.
- **No more silence**: a custom field dropped because its type is unmapped, or
  because its value does not match its declared type, is now logged as a
  warning (`THC-117`) naming both the field and the type. A future unknown type
  will be visible in the logs instead of costing a day of troubleshooting.
- **Regression tests**: the parsing routine gains its first unit tests. Every
  TheHive custom field type is now asserted to survive, and the "dropped but
  logged" behaviour is asserted too.

### 🖥️ Dashboards: the Job SID is now required ([#132](https://github.com/LetMeR00t/TA-thehive-cortex/issues/132))
- **Root cause**: "Job SID (input data)" was optional in the *Create a new
  case* and *Create a new alert* panels. Leaving it empty produced an empty
  `| loadjob`, and the failure surfaced far from its cause — a
  `FileNotFoundError` followed by `UnboundLocalError: local variable 'rf'
  referenced before assignment`, deep inside the alert action base.
- **Fix**: Splunk Simple XML has no `required` attribute, so the field now
  drives a token and the action panel depends on it. The action cannot run
  until a SID is entered, and the label carries a `*` like the other mandatory
  fields.

### ☁️ Splunk Cloud: `sc_admin` can write views and navigation
- `metadata/default.meta` granted write access on `[views]` and `[nav]` to the
  `admin` role only. Splunk Cloud customers hold **`sc_admin`**, not `admin`,
  so those knowledge objects were unreachable for them. Both roles are now
  granted, matching what the app-level stanza already did.

### 📚 Documentation ([#128](https://github.com/LetMeR00t/TA-thehive-cortex/issues/128))
- The UC2 walkthrough screenshots predate the v4.0.0 UCC rework: they still
  show *TheHive instance ID* as free text and *Alert mode* as radio buttons,
  where both are now dropdowns named **Instance** and **Alert mode**.
- The screenshots could not be regenerated for this release, so the section now
  carries the **field values in writing**, read off the images themselves,
  including the fact that `Severity`, `TLP`, `PAP` and `Scope` are dropdowns
  rather than field names, and that `Description` expects the **name of the
  field** holding the text (`info` in the UC2 search).

## Under the hood

These change nothing for users, but matter to anyone building the add-on:

- **`splunktaucclib` 8.1.0 → 8.2.0**, the minimum accepted by `ucc-gen` 6.5.3.
  Building with an older pin fails before any code is compiled.
- **`package/lib/requirements.txt` is now versioned.** It was silently excluded
  by the generic `lib/` rule of the Python `.gitignore`, which meant a fresh
  clone could not rebuild the same add-on.
- **The test suite is now part of the repository.** The unit tests mock every
  Splunk and network module and run anywhere; the integration tests read their
  endpoints and credentials from a local `.env`, which stays out of the
  repository.
- `CONTRIBUTE.md` gains the **AppInspect step**, which the build/package/deploy
  lifecycle did not describe.

## Splunk Cloud vetting

Measured with AppInspect **4.3.0** (`--mode precert --included-tags cloud`) on
the packaged `.spl`:

| | |
| :--- | :--- |
| `error` / `failure` | **0 / 0** |
| `future_failure` | 1 |
| `warning` | 15 (all informational) |
| `success` | 136 |

The remaining `future_failure` is `check_for_custom_mako_templates`, on
`appserver/templates/base.html`. **It cannot be fixed from this repository**:
the file does not exist in the sources — `ucc-gen` generates it, the latest
release (6.5.3) still does, and three generated views reference it
(`configuration.xml`, `dashboard.xml`, `inputs.xml`). AppInspect advises
regenerating with UCC ≥ 6.3.0, which does not remove it. It becomes blocking
with Splunk Enterprise 10.4; the fix has to come from a future UCC release.

## Deployment Notes
- **Prerequisite**: Python 3.9 (matches Splunk's bundled interpreter).
- **Migration Path**:
    - **From v4.2.1 / v4.2.0 / v4.1.0 / v4.0.0**: non-breaking update. Existing
      configuration, accounts, instances and certificates are preserved.
    - **From v3.9.0 (Direct Upgrade)**: you can upgrade directly to v4.2.2.
    - **⚠️ CRITICAL**: if upgrading from v3.x, the
      **[v4.0.0 migration instructions](./v4.0.0.md) are mandatory** and remain
      valid for this version (UCC architecture migration, breaking configuration
      changes, and new credential storage). Please read them carefully before
      proceeding.
- **After upgrading**: if you use a custom field of type `url` in an alert
  action, it will start arriving in TheHive — check that the receiving custom
  field is the one you expect.
- **Upgrade tip (Windows / on-prem)**: never delete the app's `local/` folder.
  Stop Splunk, back up `local/`, deploy the new build, restore `local/`, then
  start Splunk.
