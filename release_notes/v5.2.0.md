# Release Notes - v5.2.0: "Don't Bee Repetitive" 🐝

## Summary

Splunk stops re-sending alerts TheHive already holds, and the add-on stops
retrying them. A scheduled search over a sliding window, or a notable that stays
"New", is sent again on every run; TheHive refuses the copy, and the add-on used
to retry that refusal three times in a row. Reported on a production instance:
5,101 refused creations in 24 hours for 40 distinct alerts.

## New

* **"Notable status once sent"** (alert action *Create a new alert*, new
  optional parameter `notable_status`). Once TheHive holds the alert (created
  now, or already there), the add-on sets the Splunk ES notable to that review
  status ID, so the correlation search no longer picks it up. Empty by default:
  nothing changes unless you fill it in. ES mode only. The Splunk user running
  the action needs the `edit_notable_events` capability. A failure here is logged
  (WARNING `THCA-128` / `THCA-129`) and never fails the alert: it already exists.

## Fixes

* **"Already exists" is a success, not a failure to retry.** On an alert refused
  with 409 or an "already exists" message, the add-on stops at once (INFO
  `THCA-122`) instead of repeating the refusal `thehive_creation_max_retry + 1`
  times. A bare 400 is **not** taken for a duplicate: a malformed payload also
  answers 400 and stays a failure. Cases keep their previous behaviour.

## Compatibility

| | Minimum | Tested with this release |
| :--- | :--- | :--- |
| TheHive | 5.2.0 | 5.x (lab instance) |
| Cortex | 3.0.0 | not retested (no instance) |
| Splunk | 9.3 (Python 3.9 or 3.13) | Enterprise **10.6.1** + ES 8.4.0 (Python 3.13) |

**Splunk 10.4 to 10.6.** This release was run end to end on Splunk Enterprise
10.6.1: 311 unit tests and the `tests/e2e/` campaign (10 cases, 9 passed, 1
skipped for lack of a Cortex instance), including the two new cases below. Splunk 10.4 itself was not
installed: it sits between 10.2.1 (5.0.0 and 5.1.0) and 10.6.1 (this release),
both tested. The configuration pages are served by Splunk's own page shell on
10.6, so the deprecated `base.html` Mako template is no longer on the path.
⚠️ The test harness had to change for 10.6: Splunk now rejects the impossible
cron `0 5 31 2 *`; the campaign uses `0 5 29 2 *`.

**AppInspect** (precert, cloud tags, 4.3.1): 0 error, 0 failure, 0 future
failure, 16 warnings (including `check_for_custom_mako_templates`), 138 success.

**The two new behaviours were exercised for real**, not only in unit tests:
`e2e_notable_es.py` makes Splunk ES create a genuine notable, sends it with
`notable_status`, checks that TheHive holds one alert whose sourceRef is the
notable's `event_id` and that the notable really moved from *New* to *In
Progress*, then sends it again: TheHive refuses it (HTTP 400 "already exists"),
the add-on logs `THCA-122`, does not retry, and the notable stays handled.
`e2e_sliding_window.py` does the same with three overlapping runs (A, A+B, B+C):
three alerts, exactly two refusals, no retry. Both were seen failing first
(`notable_status` emptied: the notable stays *New*).
